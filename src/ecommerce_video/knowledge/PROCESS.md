# 知识库制作流程 SOP（v1.0）

> 定位：knowledge/ 的**建设与维护手册**。解决两个问题：
> ① 一次输出太多 → 内容漂移（字段不一致/提示词敷衍/校验遗漏）
> ② 品类规模与知识库大小如何规划（不盲目堆量）
> 适用范围：新增品类、扩充子品类、修正既有条目。

---

## 1. 规模模型（品类数 × 知识库大小）

### 1.1 一个品类的知识 = 3 件套

| 件 | 文件 | 内容量 |
|---|---|---|
| ① 品类知识包 | category-profiles.json 的 1 个 profile | 固定 8 块（字段集/锚点/材质推断/动态词库/质检/负面词/合规引用） |
| ② 场景光线对照 | {品类}-scene-light.json 的 N 条 | N ≈ 子品类数 × 1.5 |
| ③ 索引注册 | index.json 1 个 entry + 检索路径 | 固定 2 处 |

### 1.2 规模分级（按品类数规划工作量）

| 级别 | 品类数 | 预估条目总量 | 说明 |
|---|---|---|---|
| Core | ≤5 | ≤120 条 | 服装/美妆/食品/3C/家居（已完成） |
| Standard | ≤10 | ≤220 条 | + 鞋靴/箱包/配饰/个护/母婴（已完成） |
| Full | ≤15 | ≤300 条 | + 运动/宠物/汽车/珠宝（已完成 14 品类，190 条） |
| 扩展 | 15+ | 每品类 +15~25 条 | 小众品类按需新增（文具/乐器/礼品/建材/图书） |

**规则：不提前建不接的品类。** 客户没需求的小众品类，只在 category-profiles 留一个 profile 骨架，场景光线对照等真接单再建。

### 1.3 单品类规模参考（已有数据）

| 品类 | 子品类数 | 对照条目 | 实际比例 |
|---|---|---|---|
| 服装 | 20+ | 30 | 1.5× |
| 美妆 | 10 | 15 | 1.5× |
| 食品 | 12 | 17 | 1.4× |
| 3C | 9 | 13 | 1.4× |
| 配饰 | 4 | 6 | 1.5× |
| 宠物 | 5 | 7 | 1.4× |

→ **经验公式：条目数 = 子品类数 × 1.5（取整），每个子品类至少 1 条。**

## 2. 制作流程（5 阶段，逐批推进）

```
P0 规划 → P1 模板锁定 → P2 分批制作 → P3 校验 → P4 验收存档
```

### P0 规划（一次会话，只出清单不出内容）

1. 定品类清单与优先级（客户需求驱动）
2. 按 1.3 公式定每个品类的条目数
3. 列**条目清单**：只有 id / name / 分组 / 一句话定位，无内容
4. 用户确认清单后才进入制作

**产出**：《品类×条目规划表》（见文末模板）

### P1 模板锁定（每品类一次，锁定后不动）

1. 选该品类 1 个代表性条目做 **Golden Sample**（完整 8 字段）
2. 锁定：字段顺序、命名风格（id 小写英文）、提示词语气（中文、动作+质感）、负面词颗粒度（≥3 条具体词）
3. Golden Sample 写入该文件头部作为示例注释

**防漂移关键：Golden Sample 是后续所有条目的对照基准。**

### P2 分批制作（核心节奏控制）

| 批次大小 | 适用 | 原因 |
|---|---|---|
| 5 条/批 | 常规 | 单次输出甜区，质量可控 |
| ≤8 条/批 | 子品类少（≤4个） | 结构相似，风险低 |
| 3 条/批 | 复杂品类（服装/珠宝） | 细节多，逐条精修 |

**每批流程**：
1. 先发条目 id 列表（无内容）→ 确认结构
2. 逐条填写 8 字段（对着 Golden Sample 逐字段核对）
3. 批内自查：id 唯一、字段齐全、提示词含动作+质感、避坑具体到该产品
4. 立即校验（P3 的命令）→ 通过才继续下一批

### P3 校验（每批必跑，命令固定）

```bash
node -e "const fs=require('fs');const j=JSON.parse(fs.readFileSync('knowledge/xxx.json','utf8'));const items=j.items;console.log('条目数:',items.length);const ids=items.map(i=>i.id);console.log('id重复:',ids.length===new Set(ids).size?'无':'有!');const must=['id','name','properties','scenes','light','prompt_zh','avoid','negative','tags'];items.forEach(i=>{const miss=must.filter(k=>!(k in i));if(miss.length)console.log('缺失字段:',i.id,miss)})"
```

校验项：
- [ ] JSON 语法有效
- [ ] id 唯一且小写英文
- [ ] 8 字段齐全（对照 Golden Sample）
- [ ] prompt_zh 含动作描述 + 质感描述
- [ ] avoid 是"具体产品级"避坑（不是"注意一致性"这种空话）
- [ ] negative ≥3 条且含品类专属词
- [ ] tags 与 index.json 检索路径能对上

### P4 验收存档

1. index.json 注册新文件（内容/条目数/分组/tags/id_prefix/typical_query）
2. category-profiles.json 的 scene_light_tendency 指向新文件
3. 跑全库校验（19 文件全量 parse）
4. memory 记录：新增品类、条目数、校验结果
5. 标记该品类"可用"（客户接单时查 knowledge 优先用已验收品类）

## 3. 防漂移机制（对照清单）

| 漂移症状 | 机制 |
|---|---|
| 字段结构不一致 | Golden Sample 逐字段对照（P1 锁定） |
| 提示词空洞/重复 | 每批校验 prompt_zh 必须含"动作+质感" |
| 避坑敷衍（"注意一致"） | 校验 avoid 必须具体到该产品 |
| 负面词凑数 | 校验 ≥3 条 + 品类专属词 |
| id/命名混乱 | 校验小写英文 + 唯一 |
| 检索断裂 | P4 检查 index.json + category-profiles 引用 |
| 一次输出过多 | P2 批次限制 5-8 条 |
